# Выбор архитектуры перекачки данных в ClickHouse

[English](data-loading.md) | [Русский](data-loading.ru.md)

Этот документ фиксирует рассмотренные альтернативы для переноса изменений из Postgres в ClickHouse и причины, по
которым выбран официальный **Kafka Connect ClickHouse Sink Connector** (см.
[`docs/data-analytics/README.ru.md`](README.ru.md) для текущей реализации).

---

## Критерии сравнения

* **Согласованность данных** — не должно быть потери или дублирования строк при сбоях воркера/сети.
* **Нагрузка на OLTP** — перекачка не должна создавать дополнительную нагрузку на продакшен-базу Postgres.
* **Поддержка удалений и обновлений** — изменения и `DELETE` в источнике должны быть видны в ClickHouse.
* **Объём собственного кода** — предпочтение отдаётся готовому, проверенному индустрией компоненту перед
  кастомным воркером, если это не ограничивает нужную гибкость.

---

## Рассмотренные альтернативы

### 1. Кастомный воркер с инкрементальным опросом (`SELECT WHERE id > max_id`)

Периодический воркер раз в N минут выбирает из Postgres записи с ID/датой больше максимального значения,
уже присутствующего в ClickHouse, и заливает их батчами через канал (`System.Threading.Channels`).

**Отклонено**, так как:
* **Hard Deletes не видны.** Удаление строки в Postgres никак не отражается в инкрементальном `SELECT` по
  возрастающему ID — в ClickHouse остаются «зомби-записи».
* **Updates старых строк пропускаются.** Обновление строки с уже перенесённым (маленьким) ID не попадёт в
  следующую выборку без дополнительного индекса по `UpdatedAt`, что создаёт тяжёлую нагрузку на индексацию в
  Postgres.
* **Периодическая нагрузка на OLTP-базу.** Каждый опрос — это полноценный аналитический `SELECT` на боевой базе,
  в отличие от асинхронного чтения WAL-лога, которое создаёт нулевую нагрузку на движок СУБД.

### 2. Кастомный воркер поверх Debezium CDC-потока

Вместо периодического `SELECT` — воркер, вычитывающий уже готовый CDC-поток Debezium из Kafka и батчами
заливающий его в ClickHouse через `System.Threading.Channels`.

**Отклонено в пользу готового коннектора**, так как индустриальный стандарт для этой задачи — официальный
Kafka Connect Sink, а не кастомный код: коннектор уже решает батчинг, управление офсетом и ретраи, не оставляя
простора для ошибок в домашней реализации того же самого протокола. Для пайплайнов, где нужно сопоставлять схемы
разнородных СУБД (например, различающиеся типы данных или диалекты), кастомный воркер с явным маппингом полей
«в лоб» остаётся оправданным выбором — но для однородного пайплайна Postgres → ClickHouse в этом проекте такой
необходимости нет.

### 3. Официальный Kafka Connect ClickHouse Sink Connector (выбрано)

Коннектор вычитывает из Kafka-топика пачку сообщений, не коммитит офсет, пока пачка не подтверждена ClickHouse
(`HTTP 200 OK`), и только после этого продвигает офсет. При сбое на любом шаге коннектор перечитывает тот же
офсет после перезапуска — гарантия **at-least-once**. Повторно присланные строки схлопываются в ClickHouse
автоматически за счёт `ReplacingMergeTree` + `non_replicated_deduplication_window`, что в сумме даёт финальную
консистентность без потери строк и без лишней OLTP-нагрузки — все критерии сравнения выше закрыты без
дополнительного кода.

Подробности реализации и схема данных — в [`docs/data-analytics/README.ru.md`](README.ru.md).
