# Хаос-инжиниринг, нагрузочное тестирование и горизонтальное масштабирование

[English](README.md) | [Русский](README.ru.md)

Сервисы-воркеры работают в нескольких репликах, Kafka направляет сообщения на реплики по ключу партиции, а
повторяемый стенд нагрузки и внесения отказов проверяет, что ни одна финансовая запись не потеряна, не дублирована и
не повреждена при убийстве реплик и деградации Redis.

---

## 1. Топология горизонтального масштабирования

| Сервис | Реплики (Compose / Helm) |
| :--- | :--- |
| `AccountBalance.Service` | 3 |
| `SagaOrchestrator.Service`, `Compliance.Service`, `CoreLedger.Service` | по 2 |
| `Gateway.Api`, `Processing.Api` | 1 |

В каждом топике 12 партиций (`PARTITIONS` в провижонере Compose, `kafka.topicPartitions` в Helm): число делится
поровну на 2, 3, 4 или 6 реплик одной consumer-группы. Все producer'ы проставляют ключ партиции (`AccountId` или
`TransactionId`), поэтому один счёт или одна транзакция всегда обрабатывается одной репликой в порядке отправки.
Выбор ключей и проверка: [`docs/scaling/kafka-partition-keys.ru.md`](../scaling/kafka-partition-keys.ru.md).

Prometheus находит реплики через DNS service discovery (`dns_sd_configs`): имя сервиса Compose и headless-сервис
`*-pods` в Helm возвращают по одному адресу на реплику. Порты реплик на хосте в Compose выделяются из диапазонов
`6010-6019` (оркестратор), `6020-6029` (баланс), `6030-6039` (compliance) и `6040-6049` (ledger); список —
`docker compose ps`.

## 2. Дизайн Exactly-Once обработки

Kafka доставляет «минимум один раз», поэтому exactly-once *эффекты* обеспечиваются идемпотентными потребителями и
коммитом offset'ов только после завершения работы и публикации события-результата.

| Шаг | Защита от дублей и сбоев |
| :--- | :--- |
| Hold, Top-up, Confirm, Release (`AccountBalance.Service`) | Каждый потребитель проверяет наличие записи журнала по транзакции и повторяет событие-результат вместо повторной проводки. Транзакционная advisory-блокировка PostgreSQL по `TransactionId` (и по каждому затрагиваемому счёту, в порядке возрастания) сериализует дубли и конкурентные записи на всех репликах, поэтому два писателя не читают один и тот же максимальный номер последовательности. `HoldAccountBalanceConsumer` дополнительно удерживает Redis RedLock на счёт. |
| Запись в ledger (`CoreLedger.Service`) | В `LedgerEntries` есть уникальный индекс по `TransactionId`, вставка выполняется как `ON CONFLICT DO NOTHING`, поэтому повторно доставленная команда не создаёт вторую запись. Компенсация `WriteAuditTrail` удаляет запись, поэтому транзакция с откатившимся routing slip не оставляет записи в ledger. |
| Routing slip (`CoreLedger.Service`) | `WriteLedgerRecordConsumer` ждёт (до 30 с), пока in-memory Courier routing slip завершится и событие-результат попадёт в Kafka; отслеживание выполняет `LedgerRoutingSlipCompletionRegistry`. Пока slip выполняется, offset Kafka не коммитится: убитая посреди slip реплика приводит к повторной доставке на здоровую реплику, которая заново выполняет идемпотентный slip. Slip, не уложившийся в таймаут, повторяется три раза с интервалом 2 с. |
| Сага (`SagaOrchestrator.Service`) | Дубликаты и запоздавшие события (например, после повторной доставки) игнорируются в любом состоянии, а не роняют потребителя. Сам переход состояния защищён транзакционным outbox и inbox EF Core. |

Redis используется только как дополнительная блокировка и кэш. Корректность журнала от него не зависит: даже если
Redis потерял или задержал блокировку, advisory-блокировки PostgreSQL и уникальные ограничения сохраняют журнал
согласованным.

## 3. Инструменты

| Путь | Назначение |
| :--- | :--- |
| [`tests/chaos/k6/ledger-load.js`](../../tests/chaos/k6/ledger-load.js) | Скрипт k6: нагрузка с постоянной интенсивностью, 85% дебетовых саг и 15% пополнений, поддерживающих равновесие денежной массы (см. [`load-testing-topup-strategy.md`](load-testing-topup-strategy.md)). Пишет JSON-сводку с числом подтверждённых транзакций. |
| [`tests/chaos/scripts/prepare-accounts.sh`](../../tests/chaos/scripts/prepare-accounts.sh) | Создаёт и пополняет пул счетов и записывает их идентификаторы для k6. |
| [`tests/chaos/scripts/run-chaos.sh`](../../tests/chaos/scripts/run-chaos.sh) | Запускает один сценарий: нагрузка k6, внесение отказа и сверка. |
| [`tests/chaos/scripts/reconcile.sh`](../../tests/chaos/scripts/reconcile.sh) | Ждёт завершения незавершённых саг и проверяет инварианты из раздела 5. |
| `infrastructure/toxiproxy/toxiproxy.json` | Прокси Toxiproxy `redis` (`:6380` на Redis) для сетевых отказов. |

Скриптам нужны `bash`, `docker`, `curl` и `awk`; для Kubernetes-бэкенда также `kubectl`. k6 запускается из образа
`grafana/k6`, локальная установка не требуется. Нагрузка идёт напрямую в `Processing.Api` (порт `5201`, Kind: `15201`),
чтобы измерять конвейер саг, а не лимиты edge-слоя.

## 4. Сценарии

| ID | Сценарий | Внесённый отказ | Ожидаемое поведение |
| :--- | :--- | :--- | :--- |
| CFT-01 | `baseline` | нет | Каждая подтверждённая транзакция достигает `Completed` или `Failed`; инварианты выполняются. |
| CFT-02 | `kill-balance` | `docker kill` / `kubectl delete pod --grace-period=0 --force` реплики `AccountBalance` дважды под нагрузкой | Kafka переназначает партиции, оставшаяся реплика идемпотентно повторно обрабатывает некоммитнутые записи. |
| CFT-03 | `kill-ledger` | то же для реплики `CoreLedger`, которая может погибнуть посреди routing slip | Незавершённый slip доставляется повторно и выполняется заново; нет ни дубля, ни «осиротевшей» записи ledger. |
| CFT-04 | `kill-orchestrator` | то же для реплики `SagaOrchestrator` | Выжившая реплика продолжает саги из сохранённого состояния. |
| CFT-05 | `redis-latency` | задержка Toxiproxy 2,5 с ± 1,5 с на каждом соединении с Redis в течение 30 с | Получение блокировок замедляется или завершается ошибкой, затронутые саги заканчиваются `Failed` с освобождённым холдом; повреждений нет. |
| CFT-06 | `redis-blackhole` | токсик `timeout` Toxiproxy (соединения открыты, байты не идут) в течение 20 с | Как CFT-05 на время разрыва; после него система восстанавливается. |

Бизнес-отказы (недостаточно средств, правила compliance) завершают сагу в `Failed` с компенсированным холдом; это
часть ожидаемого набора исходов, а не ошибки.

### Запуск

```bash
# Docker Compose: запуск стенда, масштаб задан в docker-compose.yml
docker compose up -d --build
tests/chaos/scripts/run-chaos.sh baseline 2m
tests/chaos/scripts/run-chaos.sh kill-ledger 3m

# Сценарии с Redis направляют все соединения с Redis через Toxiproxy
REDIS_ENDPOINT=integration-bus-toxiproxy:6380 docker compose --profile chaos up -d
tests/chaos/scripts/run-chaos.sh redis-latency 2m

# Kubernetes (Kind)
helm upgrade --install integration-bus deploy/k8s/charts/integration-bus -n integration-bus --create-namespace \
  --set chaos.toxiproxy.enabled=true
BACKEND=k8s tests/chaos/scripts/run-chaos.sh kill-ledger 3m
```

`TARGET_RPS` (по умолчанию `200`) и `ACCOUNT_COUNT` (по умолчанию `300`) настраивают нагрузку. Артефакты запуска
пишутся в `tests/chaos/work/<сценарий>/` (игнорируются git).

## 5. Инварианты согласованности

`reconcile.sh` завершается с ненулевым кодом, если нарушен любой инвариант.

| Инвариант | Смысл |
| :--- | :--- |
| Число принятых транзакций равно числу саг | Каждый HTTP `202` породил ровно один экземпляр саги: ничего не потеряно. |
| Нет саг в нетерминальном состоянии | Каждая сага достигла `Completed` или `Failed` после периода дренажа. |
| Сумма журнала равна сумме пополнений | Холды, релизы и подтверждения только перемещают средства: деньги не создаются и не исчезают. |
| Нет отрицательных балансов и дублей номеров последовательности | Журнал event sourcing остался согласованным при конкурентных записях. |
| Сага `Completed`: 1 холд, 2 подтверждения, 0 релизов, 1 запись ledger | Перевод проведён ровно один раз на обоих счетах и в ledger. |
| Сага `Failed`: 0 подтверждений, 0 записей ledger, холд полностью освобождён | Неуспешная транзакция не оставила финансового следа. |
| Нет записей журнала или ledger без саги | Нет «осиротевших» записей. |

## 6. Руководство по эксплуатации

| Симптом | Действие |
| :--- | :--- |
| Саги остаются в состоянии `Awaiting*` после периода дренажа | Проверьте, что все реплики запущены (`docker compose ps`, `kubectl get pods`), и посмотрите отставание потребителей в Kafka UI (`http://localhost:8080`). Упавшая реплика задерживает только свои партиции до перезапуска или перебалансировки группы. |
| `reconcile.sh` сообщает о расхождении числа принятых транзакций | Сводка k6 считает ответы HTTP `202`. Перезапускайте с тем же `WORK_DIR` только после удаления `k6-summary.json`; окно запуска определяется по часам базы данных, поэтому параллельный трафик другого клиента завышает число саг. |
| Сценарии с Redis завершаются сообщением «Toxiproxy is not reachable» | Запустите стенд с профилем chaos и `REDIS_ENDPOINT` (Compose) или `chaos.toxiproxy.enabled=true` (Helm). |
