# 🗺️ Roadmap эволюции `integration-bus` к финтех-платформе

## Принцип построения последовательности

Каждая следующая задача **опирается** на результат всех предыдущих — ни одна не вынесена "потому что она маленькая", если у неё есть реальная технологическая зависимость. Три фазы расположены в порядке, который прямо запросил заказчик:

- **Фаза 1 — Инфраструктура и архитектурный фундамент.** Ничего из этого не видно конечному бизнес-пользователю напрямую, но без этого фундамента фазы 2 и 3 либо невозможны, либо потребуют дорогостоящего рефакторинга задним числом (миграции схем БД, протаскивание мультитенантности через уже написанный код и т.п.).
- **Фаза 2 — Бизнес-логика собственной разработки.** Всё, что можно полностью написать и протестировать локально, без ключей API, без аккаунтов у третьих лиц, без сетевых вызовов наружу (кроме наших собственных Docker-сервисов вроде Gotenberg/MinIO).
- **Фаза 3 — Внешние интеграции.** Всё, что требует реального (пусть и тестового/sandbox) аккаунта у внешнего провайдера или специфичной региональной инфраструктуры. 

  > 🏛️ **Архитектурный манифест Фазы 3:** Чтобы проект оставался глобальным System Design решением, мы строго разделяем бизнес-логику и вендоров. Все внешние системы скрыты за абстракциями (паттерны **«Стратегия»** и **«Адаптер»**). Для обеспечения **100% автономности тестовой среды (Sandbox)**, международные коннекторы используют Open-Source эмуляторы, запускаемые локально в Docker-сети, что гарантирует работоспособность инфраструктуры из любой точки мира без VPN.

  #### Карта архитектурных абстракций и провайдеров тестовой среды:

  | Бизнес-домен (Интерфейс) | Локальный Sandbox для Docker (100% доступен) | СНГ / РФ Провайдер (Production) | Международный Провайдер (Production) | Архитектурная роль в шине |
  | :--- | :--- | :--- | :--- | :--- |
  | **IPaymentGateway** | `stripe/stripe-cli` *(Local Container)* | ЮKassa | Stripe / Adyen | Обработка распределенных транзакций, идемпотентность оплат и вебхуки. |
  | **IFiscalFormat** | `Mock-Fiscal-Server` *(Внутренний стаб)* | АТОЛ (54-ФЗ) | TaxJar / Avalara | Асинхронная фискализация чеков, управление очередью к ККМ. |
  | **IAddressValidator** | `OpenStreetMap / Nominatim` *(Self-hosted)* | DaData | Google Places / Loqate | Очистка, валидация и нормализация Master Data контрагентов при импорте. |
  | **IFxRatesProvider** | `CBR.ru API / Open Exchange Rates` | Курсы ЦБ РФ | Bloomberg / Fixer.io | ETL/CDC-импорт матриц курсов валют для мультивалютного процессинга. |
  | **IEdiAdapter** | `OpenPeppol Validator / Mock EDI` | Контур.Диадок | SAP Ariba / Peppol | Юридически значимый электронный документооборот (B2B EDI) и подписание актов. |
  | **ICryptoEngine** | `OpenSSL (X.509) / PKCS#11 Container` | КриптоПро (ГОСТ) | AWS CloudHSM / Vault | Модуль подписи документов. Поддерживает как стандартные, так и национальные ГОСТ-алгоритмы. |
  | **IIdentityProvider** | `Keycloak` *(Локальный инстанс)* | VK OAuth / Яндекс ID | Google / GitHub Auth | Федеративная аутентификация пользователей по протоколам OIDC / OAuth 2.0. |


Нумерация задач — сквозная (1…40), чтобы явно видеть единый порядок выполнения. Каждая задача эволюции помечена зависимостями «от задачи №…».

## 📦 Фаза 1. Инфраструктура и архитектурный фундамент

### Задача 1. CI-валидатор ссылок в документации (Lychee)
**Зависимости:** нет — абсолютно независимая задача, хороший «разогрев».

- Выбираем **Lychee** (Rust) — он уже сравнивается в документе с `markdown-link-check` и `muffet`; Lychee быстрее и умеет в относительные пути `.md`, что критично — у нас уже десяток перекрёстных ссылок между `docs/*.md` (`README.md` → `docs/roadmap.md` → `docs/observability/README.md` и т.д.), накопленных за эту сессию.
- Конфиг `.lychee.toml` в корне `C:\proj\integration-bus`: исключить `http://localhost:*`, `http://integration-bus-*` (внутренние docker-hostnames, встречаются в `docker-compose.yml`-примерах внутри `docs/`), таймаут 8с.
- `.github/workflows/markdown-link-checker.yml` — отдельный workflow (не трогаем существующий `ci.yml` из Stream 6), триггер `pull_request`/`push` на `main`, `fail-fast` при битой ссылке, `GITHUB_TOKEN` в env для обхода rate-limit на ссылках `github.com`.
- Документируем команду локального запуска в `README.md` в новой секции «Для разработчиков».

*Почему первой:* нулевой риск, не трогает код сервисов, сразу повышает качество документации, которую мы будем активно наращивать (ЭДО, FX, биллинг — всё это новые `docs/*.md`), пока ссылки ещё не успели «протухнуть».

### Задача 2. CQRS + MediatR — архитектурный разворот Write/Read контуров
**Зависимости:** нет жёстких, но **всё, что будет написано дальше в Фазах 2–3, должно сразу проектироваться как `IRequest`/`IRequestHandler`**, иначе придётся переписывать 20+ новых фич.

- Добавляем `MediatR` в `IntegrationBus.Shared` (или новую библиотеку `IntegrationBus.Cqrs`), три сквозных `IPipelineBehavior`:
  - `ValidationBehavior` — прогон через уже используемый у нас `FluentValidation` (в `Gateway.Api`/`Processing.Api` он уже есть по [`docs/roadmap.md`](roadmap.md) → «API Governance»).
  - `IdempotencyBehavior` — ключ `X-Idempotency-Key` в Redis (Redis у нас уже поднят и используется RedLock-ом — переиспользуем тот же `IConnectionMultiplexer`).
  - `LoggingBehavior` — через существующий Serilog/`ILogger<T>` конвейер (тот самый, который мы только что чинили для `SagaOrchestrator.Service`).
- **Важно:** существующую сагу и Courier Routing Slip **не трогаем** — MediatR здесь не заменяет MassTransit Saga State Machine, он закрывает новый контур (`Management.API`, будущий биллинг, DLQ-менеджер), где командная логика проще, чем распределённая сага.
- Все команды Фазы 2/3 (DLQ-resend, изменение лимита контрагента, ручной клиринг, биллинг-команды) с первого дня пишутся через `IRequest<TResponse>`.

*Почему второй:* ставить архитектурный каркас до появления первого реального UI/бизнес-кейса — единственный способ не переписывать 15 фич позже. Задача 1 не создаёт зависимостей, поэтому порядок 1→2 произволен, но 2 обязана идти раньше почти всего остального.

### Задача 3. Стандартизация конверта сообщений — CloudEvents
**Зависимости:** задача 2 (новые команды/события удобнее сразу заворачивать в единый конверт).

- `CloudNative.CloudEvents.SystemTextJson` — оборачиваем **новые** контракты (FX, клиринг, антифрод, биллинг из Фазы 2/3) в `CloudEvent`-конверт с метаданными (`type`, `source`, `time`, `subject`).
- **Существующие** контракты MassTransit (`HoldAccountBalance`, `WriteLedgerRecord` и т.д.) **не переписываем** — это сломает совместимость уже протестированной саги без выгоды. CloudEvents вводим только для новых потоков, где внешняя (EDM/ATOL/ЮKassa) или межкомандная совместимость реально важна.

*Почему третьей:* делать это нужно **до**, а не после появления десятка новых типов событий (FX, клиринг, антифрод) — иначе переписывать придётся сами события.

### Задача 4. Mapperly — замена ручного маппинга
**Зависимости:** задача 2 (маппинг чаще всего живёт внутри `IRequestHandler`).

- Подключаем `Mapperly` в новые сервисы (DLQ Inspector, Billing, FX) для трансформации Command → Entity → Event.
- Существующие consumers (`ConfirmAccountBalanceConsumer` и т.д.) не трогаем — там маппинг тривиальный и явный, Mapperly туда не добавляет ценности, а риск регресса есть.

---

### Задача 5. Hangfire — движок фоновых задач
**Зависимости:** задача 2 (команды ретрая/очистки — тоже `IRequest`), использует существующий Postgres (отдельная БД `hangfire_db` в `docker-compose.yml`, по аналогии с `saga_db`/`accounting_db`).

- **DLQ Retry Engine:** экспоненциальный backoff+jitter (1 мин → 5 мин → 30 мин) для сообщений, не доставленных во внешние контуры. Это и есть технический фундамент для будущего DLQ Inspector (задача 22) и для устойчивости внешних интеграций Фазы 3 (ЮKassa/ЭДО/АТОЛ неизбежно иногда недоступны).
- **Хаускипинг:** periodic job очистки логов успешно доставленных сообщений старше 30 дней — применяем к уже существующим таблицам (`JournalEntries`, `OutboxMessage`), аккуратно, чтобы не задеть `non_replicated_deduplication_window`-логику ClickHouse-пайплайна, который мы верифицировали в прошлой сессии.
- Hangfire Dashboard поднимаем за Basic Auth внутри `Management.API` (задача 11) — ещё один повод, почему Management.API идёт позже.

*Почему пятой:* почти каждая фича Фазы 2/3 (клиринг по расписанию, email-рассылка, опрос статуса АТОЛ, polling ЭДО) нуждается в планировщике фоновых задач — лучше завести его один раз сейчас.

### Задача 6. Мультитенантность — архитектурный фундамент БД
**Зависимости:** нет технических, но **это последний момент, когда её можно ввести дёшево** — до того, как появятся ещё 10+ новых таблиц (FX-счета, клиринг, диспуты, биллинг, EDM-документы) в Фазе 2/3.

- Паттерн *Logical Tenant Separation*: колонка `TenantId` во всех новых таблицах, глобальные EF Core Query Filters.
- **Важно и сознательно:** существующие таблицы (`Accounts`, `JournalEntries`, `TransactionState`, `LedgerEntries`) **не мигрируем** прямо сейчас — наша текущая система работает в однотенантном («наша компания») режиме, и агрессивная миграция не несёт немедленной бизнес-ценности. Правильная стратегия — ввести `TenantId` как **конвенцию для всего нового кода**, а ретроактивную миграцию существующих таблиц поставить отдельным, явно оценённым технически-долговым тикетом, когда появится первый реальный второй тенант.

*Почему именно здесь:* сделать это после — то есть после FX/клиринга/биллинга (которые по своей природе multi-tenant-ready, т.к. это SaaS-фичи) — будет на порядок дороже.

### Задача 7. Rate Limiting + Circuit Breaker — защита входного/выходного контура
**Зависимости:** нет прямых, но логически продолжает «инфраструктурное укрепление» задач 5–6.

- **Вход:** `Microsoft.AspNetCore.RateLimiting` (или Redis-токен-бакет через `AspNetCore.RateLimiting.Redis` — у нас уже есть Redis-кластер из RedLock-а, поэтому второй вариант предпочтительнее при горизонтальном масштабировании) на `Gateway.Api`/будущем `Management.API`.
- **Выход:** `Polly.Core` Circuit Breaker на HttpClient-пайплайнах — это прямая подготовка к Фазе 3: когда появятся реальные вызовы к ЮKassa/АТОЛ/Диадок/DaData, они обязаны идти через уже готовый Circuit Breaker, а не через голый `HttpClient`.

*Почему здесь:* должно быть готово **до** первого внешнего HTTP-вызова (Фаза 3), а значит, разумно внедрить сразу после СУБД-фундамента (задача 6), пока ещё ничего не завязано на конкретные внешние провайдеры.

---

### Задача 8. Resilience & HA — укрепление существующей инфраструктуры
**Зависимости:** задача 6 (мультитенантность уже заложена в схему — не переделывать дважды при переходе на кластер), логически идёт после «защитных» задач 5-7.

- **Postgres → Patroni-кластер** (1 Master + 2 Sync Replicas) — апгрейд наших `*_db` баз (`saga_db`, `accounting_db`, `compliance_db`, `ledger_db`) без изменения connection-string-конвенции (приложения продолжают знать только про один логический хост — Patroni/HAProxy скрывает топологию).
- **Redis → Sentinel/Cluster** — критично, т.к. на Redis у нас уже висит и RedLock (распределённые блокировки), и будущий Idempotency Behavior (задача 2), и Rate Limiting (задача 7) — потеря Redis сейчас уронит сразу три подсистемы.
- **Bulkhead Isolation** через MassTransit/Polly — изоляция будущих каналов интеграции (СБП/ЮKassa/крипто) по отдельным thread pool'ам, чтобы сбой одного внешнего провайдера (Фаза 3) не клал остальные.
- Transactional Outbox у нас **уже есть** (подтверждён `OutboxResilienceTests` в прошлой сессии) — здесь только документируем и явно связываем с HA-стратегией.

*Почему здесь, а не в самом начале:* нет смысла кластеризовать СУБД **до** того, как определена финальная схема (мультитенантность, задача 6) — иначе придётся гонять миграции на кластере дважды.

### Задача 9. Глубокая Observability — бизнес-метрики и health-контур
**Зависимости:** задачи 5–8 (появились новые компоненты — Hangfire, Patroni, Redis Cluster — которые нужно подключить к уже существующему Prometheus/Grafana).

- **Новые бизнес-метрики** через `System.Diagnostics.Metrics.Meter`: `integration_bus_transactions_total`, `integration_bus_processing_duration_seconds`, `integration_bus_financial_volume` — расширяем уже работающий `/metrics`-эндпоинт (он у нас есть во всех сервисах) новыми счётчиками, не трогая существующие .NET runtime/MassTransit метрики.
- **Расширенный `/health`:** `AspNetCore.Diagnostics.HealthChecks` с проверками Redis/Kafka/Postgres (частично уже используются — `AspNetCore.HealthChecks.NpgSql`/`.Kafka`/`.Redis` стоят в `CoreLedger.Service.csproj`) + добавляем S3-health (когда появится, задача 11 Фазы 2) по мере готовности зависимостей.
- Распределённый трейсинг **у нас уже реализован и верифицирован** (единый `TraceId` через 6 сервисов, см. `docs/observability/README.ru.md` §5) — здесь только убеждаемся, что новые компоненты (Hangfire jobs, Management.API) тоже попадают в трейс через `ActivitySource`.

### Задача 10. .NET Aspire — оркестрация для разработки
**Зависимости:** задача 9 — Aspire дублирует/дополняет то, что уже собрано в Prometheus/Grafana/Jaeger, разумно вводить, когда базовая observability стабилизирована.

Для локальной разработки Aspire Dashboard даёт единый экран «сообщение вошло → где застряло → где ошибка» без переключения между Grafana/Jaeger/Kafka UI.
- Не критично для production (там работает связка Prometheus+Loki+Jaeger), но резко ускоряет онбординг новых разработчиков на последующие 30 задач этого плана.

### Задача 11. Management.API + SPA-оболочка
**Зависимости:** задача 2 (CQRS — Management.API **целиком** строится как тонкий HTTP-слой над `IMediator.Send(...)`), задача 7 (Rate Limiting на новом публичном API), задача 9 (health-контур для нового сервиса).

- Новый проект `IntegrationBus.Management.Api` — **архитектурно изолирован** от `IntegrationBus.*.Service` (критическое требование документа-источника: фронтенд никогда не достаёт до `SagaOrchestrator`/Kafka напрямую). Работает со служебными БД, логами аудита, конфигурацией правил — то есть с таблицами, которые появятся в последующих задачах (лимиты — уже частично есть через RulesEngine JSON, но без UI).
- SPA `integration-bus-dashboard/` на React + TypeScript + Vite, структура ровно как в документе: `features/{dlq-inspector,mapper,routing,finance}/`, `services/` (клиент к Management.API).
- На этом этапе — **только каркас и первая закрывающая страница** (например, Health/Status dashboard, т.к. backend для неё уже полностью готов — задача 9). Остальные панели (DLQ Inspector, Mapping Designer, Reconciliation Dashboard, Routing Builder, Billing Matrix, E2E Tracer) добавляются **по мере готовности** соответствующей бэкенд-фичи — см. задачу 31 в Фазе 2, где они подключаются одна за другой.

*Почему именно сейчас, а не раньше:* ставить фронтенд до появления CQRS-слоя означало бы либо городить контроллеры напрямую поверх MassTransit (архитектурно запрещено документом-источником), либо переписывать Management.API сразу после задачи 2.

### Задача 13. QA/CI-контур — SonarCloud + Playwright + Allure
**Зависимости:** задача 11 — Playwright тестирует реальный UI, которого не было до Management.API; задача 12 — общая инфраструктура публикации статических отчётов (`gh-pages`).

- `SonarSource/sonarcloud-github-action` в существующий `.github/workflows/ci.yml` (Stream 6 из прошлой сессии) — Quality Gate: покрытие нового кода ≥80%, 0 критических уязвимостей, дублирование <3%.
- Новый проект `IntegrationBus.E2ETests` (`Microsoft.Playwright.NUnit`) — первые сценарии: логин в Management.API → health dashboard. Полноценные сценарии (DLQ resend, настройка лимитов) добавляются по мере появления соответствующих панелей (задача 31).
- `Allure.Xunit` — размечаем **уже существующие** 7 тестовых проектов (119 тестов) атрибутами (`[AllureFeature]`/`[AllureStory]`), чтобы с первого дня иметь живой, а не пустой отчёт.

*Почему это последняя задача Фазы 1:* она логически замыкает инфраструктурный контур — весь фундамент (CQRS, Hangfire, мультитенантность, HA, Management.API) должен существовать, чтобы было что проверять статическим анализом и E2E-тестами.

## 🧩 Фаза 2. Бизнес-логика собственной разработки (без внешних интеграций)

### Задача 14. Переход леджера на двойную запись + неизменяемость
**Зависимости:** задача 8 (HA — переписывать схему леджера удобнее на уже стабилизированной топологии БД), задача 6 (мультитенантность — новая схема сразу проектируется tenant-aware).

Это **самая фундаментальная** бизнес-задача всего плана — почти все дальнейшие финтех-фичи (FX, клиринг, диспуты, биллинг) требуют настоящего двойного учёта, а не текущего `LedgerEntries(TransactionId, Amount, CreatedAt)` в `CoreLedger.Service`.

- **Double-Entry Bookkeeping:** каждая операция — минимум 2 проводки (Дебет/Кредит), `Σ Дебет = Σ Кредит`. Расширяем `LedgerEntryEntity` (или заводим новую таблицу `LedgerPostings`) полями `AccountId`, `Direction (Debit/Credit)`, `Amount`, `TransactionId`.
- **Криптографическая цепочка хэшей:** каждая новая запись хранит `SHA256(PreviousRowHash + CurrentRowData)` — по аналогии с блокчейном, что исключает скрытую правку суммы даже администратором БД.
- **Запрет `UPDATE`/`DELETE`:** на уровне БД (Postgres `REVOKE UPDATE, DELETE` для роли приложения + at triggers) и на уровне кода (`WriteAuditTrailActivity` уже делает только `INSERT` — модель поведения расширяем на весь леджер). Ошибочная проводка отменяется исключительно сторнирующей (компенсирующей) записью — этот принцип уже частично реализован в `ReleaseAccountBalanceActivity`/`ReleaseAccountBalanceConsumer` (компенсация через новую запись, не правку старой) — распространяем его на `CoreLedger.Service`.
- Тесты: продолжаем паттерн Testcontainers.Postgres из `IntegrationBus.CoreLedger.Service.Tests` (уже созданного в прошлой сессии) — добавляем проверку, что сумма дебетов строго равна сумме кредитов на срезе любой транзакции, и что хэш-цепочка не ломается.

### Задача 15. Антифрод и Compliance: Velocity Checks + AML Blacklists
**Зависимости:** задача 14 (проверки идут **до** попадания проводки в леджер), переиспользует Redis (уже есть под RedLock).

- Паттерн Chain of Responsibility: новый пайплайн валидаторов **перед** `CheckComplianceLimitsActivity` (существующий RulesEngine-движок в `Compliance.Service` остаётся первым уровнем проверки лимитов; Velocity/AML — это второй, дополняющий уровень, а не замена).
- *Velocity Checks:* Redis-счётчики (частота/объём за окно времени) — естественное расширение инфраструктуры, уже используемой RedLock-ом.
- *AML Blacklists:* таблица заблокированных идентификаторов (IP/карта/кошелёк/контрагент), статус `FraudBlocked` как новое терминальное состояние саги (аналогично существующему `Failed`).

### Задача 16. FX Engine (ядро) — мультивалютные счета и спред
**Зависимости:** задача 14 (двойная запись — без неё мультивалютный кросс-платёж физически нельзя корректно провести), задача 15 (антифрод должен видеть и мультивалютные операции).

- Привязка `Account` к ISO 4217 (сейчас `Currency` enum у нас уже есть и используется — расширяем, а не изобретаем заново).
- **Важно для правильной последовательности:** на этом этапе `IExchangeRateProvider` реализуется **mock/детерминированным провайдером** (статическая таблица курсов или настраиваемый фейк в `appsettings`) — реальный провайдер (ЦБ РФ/биржи) появится в Фазе 3 (задача 36) и будет подключён через DI без изменения бизнес-логики FX Engine. Это стандартный приём «порт/адаптер», который мы уже применяли для `ITopicProducer<T>` в тестах (`RecordingTopicProducer`/`FlakyTopicProducer`).
- Кросс-валютный процессинг: hold в валюте-источнике → расчёт спреда → зачисление в валюте-приёмнике по двойной записи (задача 14) → спред на доходный счёт платформы.

**Зависимости:** задача 14 (двойная запись — источник данных для агрегации), задача 5 (Hangfire — `ClearingJob` по расписанию).

**Зависимости:** задача 22 (штамп ЭЦП как графика уже готов — здесь подключаем реальную подпись вместо заготовки-плейсхолдера).

### Задача 36. Генерация закрывающих документов + шлюз ЭДО (Диадок/СБИС)
**Зависимости:** задачи 21–23 (шаблоны/PDF/S3), 34 (верные реквизиты контрагента из DaData), 35 (подпись).

Самая сложная интеграция плана — собирает воедино почти весь стек Фазы 2:
- Hangfire recurring job (задача 5) по итогам месяца формирует через Fluid+Gotenberg (задача 21) PDF-акты сверки по данным леджера (задача 14).
- `IEdmProvider` — слой абстракции над Диадок/СБИС (легко добавить второго провайдера без изменения ядра).
- Загрузка в черновик оператора → ЭЦП (задача 35) → отправка контрагенту → фоновый воркер слушает webhooks/опрашивает статусы («Доставлено»/«Подписано»/«Отказ») → синхронизация с леджером.

### Задача 37. Реальные курсы валют — замена mock-провайдера FX Engine
**Зависимости:** задача 16 (FX Engine уже спроектирован под `IExchangeRateProvider` как порт).

- Основной путь: официальное API ЦБ РФ / биржевые API — фоновый воркер (Hangfire, задача 5) кэширует курсы в Redis с коротким TTL.
- Fallback для банков без API: `HtmlAgilityPack`-скрапинг их публичных страниц курсов — именно это обращение к неконтролируемому внешнему ресурсу (а не сама библиотека) делает сценарий внешней интеграцией, в отличие от задачи 29.
- Подключается через DI без единой строчки изменений в бизнес-логике `FxEngine` (задача 16) — ровно то преимущество порт/адаптер архитектуры, ради которого mock был введён именно в таком виде на Фазе 2.

### Задача 38. Полное E2E-покрытие внешних интеграций + финализация QA-контура
**Зависимости:** все предыдущие внешние интеграции (31–37) — тестировать нечего, пока их нет.

- Playwright-сценарии теперь покрывают: оплата через ЮKassa (sandbox) → фискализация АТОЛ → появление в Reconciliation Dashboard; отправка акта в ЭДО → изменение статуса в UI.
- SonarCloud Quality Gate ужесточается до финальных целевых показателей (≥80% покрытия, 0 критических уязвимостей) теперь уже для **всего** объёма кода, включая Фазы 2–3.
- Allure-отчёт становится полноценной витриной зрелости продукта для демонстрации стейкхолдерам/работодателям.

### Задача 39. Международный комплаенс и локализация (стратегический горизонт)
**Зависимости:** задача 29 (каркас профилей комплаенса уже существует), задача 36 (ЭДО-паттерн адаптера — тот же приём для ISO 20022/Open Banking).

Намеренно вынесена в конец: это не конкретная интеграция с известным sandbox (как АТОЛ/ЮKassa/DaData), а стратегическое направление — полноценная поддержка ISO 20022 и Open Banking/PSD2 потребует реальных банковских партнёров и выходит за рамки pet-project-реализации. На этом этапе план фиксирует **точку расширения** (архитектура уже готова принять новый `ComplianceProfile`/`IEdmProvider`-подобный адаптер), но не предполагает её немедленной полной реализации.
